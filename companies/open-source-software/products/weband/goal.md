## 之后（P1，需要外设到位）
硬件对标参考设备 **V1 圆屏**（2026-11-10 决定），外设以 V1 为准，详见 `AGENTS.md` 第一节。

- M3 音频链：模拟 MEMS 麦 → 片内 audcodec ADC。**硬件链路已实测通过（2026-11-10）**：3037 模拟麦接 `VCC`→J1-5（MIC_BIAS）、`OUT`→J1-4（MIC_ADC，板上已有 2.2 µF 隔直）、`GND`→J1-1。用 SDK `audprc` 例程录音，出声时比安静时高 10–28 dB（−51 → −23 dBFS）。导出 WAV 试听正常（音调、语速无异常，2026-11-11 用户确认）。MIC_BIAS 电压本身没实测（没有万用表），但麦能正常拾音。剩下的是固件：VAD + Opus 编码录音。
  - **M3 固件已完成（2026-11-13）**：已合入 Weband `main` 并推送（`97ec141`）。结案条件：WebRTC VAD 门控 + Opus（SILK 16 kHz 24 kbit/s）分段录到 fs_region；已用超过 2/3 自动裁剪（先删已传到手机的）；5 分钟落盘；按原版 App 1.3.1 协议经 BLE 传给手机，大小与 CRC 一致、可解码、丢块重传、断线续传。以上均已真机实测通过。
  - 已知遗留（用户决定不阻塞 M3，单独立项）：桌面敲击等短促声响仍会开段（敲击 1 分钟开 4 段）。
- **Weband 不要屏幕**（2026-11-13 用户决定）：V1 的圆形反射屏（LPM012M134B）不做，不再采购屏和转接。
- V1 器件（开源硬件页，2026-11-13）：主控 SF32LB525UC6；录音存 128 MB SD NAND（MKDV1GCL-ABF）；程序 16 MB SPI NOR（PY25Q128HA）；电池 502525。
- **待办：主控降配评估（2026-11-16 用户提出）**。依据（Nano 实测，Weband `evidence/digest.md` 2026-11-16 三节）：固件不用 PSRAM（静态段 0、无 PSRAM 堆）；SRAM 系统堆最高 116,152 / 351,868 B（约 33%，OTA 收包与录音叠加时）。单从内存看，525（8 MB PSRAM）偏宽裕，换 523（4 MB），甚至不带 PSRAM 的型号也够用。
  - 约束：要片内充电，只能选 `SF32LB52x`（DS5201：520/523/525/527，有 VBUS/VBAT/VSYS 脚）；`SF32LB52X`（DS5202：B/D/E/G/J，只有 PVDD/VBATS）不带充电。依据：SDK `tools/SiliconSchema/chips/` 两份 `chip.yaml`。
  - 不带 PSRAM 又带充电的只有 SF32LB520U36（封装内 1 MB NOR，在 MPI1）。待核实：启动和分区怎么放（片内 1 MB 放不下现有固件 733 KB + DFU 区，需仍用外部 NOR）；SDK 没有用 520U36 的官方板，没有参考配置；价格差多少。
  - 523UB6 与 525 同系列同封装、只差 PSRAM 容量，改动最小（PSRAM 配置与分区表），风险最低。
  - 若重新接屏（V1 的 JDI 屏，240×240，RGB565 一帧 115,200 B，只能整行刷新）：估算（未实测，图形库堆按 48 KB 假设）两帧完整缓冲放 SRAM 会超出 344 KB 堆；523 可把显示缓冲和壁纸缓存放 PSRAM，适合；520 只能用部分行缓冲（约 50% 堆），壁纸缓存、双缓冲、大动画做不了，不推荐。定型号前要在 Nano 上跑屏幕驱动和界面实测峰值。
  - 不阻塞当前打样（`weband_hw` 5ba782a 仍按 525）。
- M4 电源（不含显示）：电源键语义 + 片内充电。**电源键部分已完成（2026-11-13，合入 main `f1de797`）**：单击灵感录音（带超时）、双击重新配对（录灵感时延后）、长按 6 s 重启。充电部分仍在 Nano 上 blocked。**充电在 Nano 上做不了**（SF32LB52JUD6 不带充电），要验充电需另购锂电版芯片的板子（如 SF32LB52-DevKit-LCD）+ 锂电池；不再买 LGS4056。
- IMU（LSM6DS3TR-C）：V1 原理图有，但 V1 固件反汇编确认不访问（2026-11-10），不对标、不排期。
- 门控误触发（新工作项，2026-11-13 立项）：区分敲击类短响与说话，结案条件为安静房间敲击测试 0 段，且说话录音（950 / 806）覆盖率不低于现状。

- 壁纸帧 `MBWP`（无屏后）：线协议上怎么处理待用户决定。
- **无屏配对：按键确认（2026-11-13 用户决定）**。真实用户通过按键完成配对，替代"屏上显示 6 位码、手机输入"。V1 固件里有现成的方式名 `button_confirm`（`pair_begin` 的 `method`，另有 `pair_result` 状态 `stale` / `cancelled` 和 `request_id` 字段），但原版 App 1.3.1 只发输码方式，所以要我们自己的 App 配合。**固件侧已完成（2026-11-14，合入 main `55a23f5`）**：App 发 `pair_begin` + `method:"button_confirm"`，60 s 内单击电源键即配对；过期回 `expired`；`pair_cancel` 按 V1 回 `cancelled` / `stale` / `invalid_request`。
- **待办：莫斯码配对（2026-11-13 用户提出）**。用敲击，或"敲击 + 划动"组成的莫斯码完成配对。识别方式已定（2026-11-13 用户）：**IMU（LSM6DS3TR-C）加麦克风**，识别敲击声和划动的摩擦声。注意：V1 固件不访问 IMU，这部分是 Weband 自己的功能；Nano 上没有 IMU，需要外接模块或用 V1 板。待定：码由谁生成、谁比对，以及与按键确认的关系。
- **待办：无蜂鸣器（2026-11-16 用户提出）**。Weband 板上没有蜂鸣器（V1 原理图也没有），固件不能靠声音提示。配对确认、录音开关、重新配对、低电量、OTA 等需要用户感知的状态，要改用 LED（PA31/PA32）闪烁模式表达；各状态的闪法和是否需要其它反馈方式（如振动）待定。
